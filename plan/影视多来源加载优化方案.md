# TVBox 影视多来源加载优化方案

> 制定日期：2026-08-25<br>
> 实施范围：Android 主应用 `app/` 的 MacCMS 首页、搜索、详情与播放源补齐流程。

## 目标

- 让搜索页在首个来源返回后立刻展示影片卡片，而不是等待全部来源。
- 让详情页优先展示当前来源的详情和可播放剧集，其他来源在后台逐步补齐。
- 避免低性能电视盒子同时发起过多请求，并降低上游接口的 429、超时和重复请求。
- 保持首页分类的来源一致性，避免不同站点的分类 ID 混合。

## 当前实现结论

| 场景 | 原行为 | 主要问题 |
|---|---|---|
| 首页分类 | 只请求当前选中来源 | 单源稳定，但缺少列表缓存 |
| 普通搜索 | 只请求当前选中来源 | 无法利用其他来源补全结果 |
| 影片详情 | 其他来源使用并发查询 | 通过 `awaitAll()` 等待全部完成，最慢来源拖住详情页 |
| 单来源备用网址 | 顺序尝试备用网址 | 此逻辑适合作为单来源容灾，保留即可 |

## 定制策略

```text
首页分类：当前主来源 + 短期内存缓存

搜索：主来源优先；全部可用来源以最多 3 条并发检索；每条完成立即合并和显示

详情：先显示主来源；其余来源以最多 3 条并发匹配；每匹配到一个播放源立即更新详情页

调度：失败来源进入短期冷却；成功且响应快的来源在后续搜索中优先
```

## 实施内容

### 1. 受控并行搜索

- 使用 Kotlin 协程的 `Semaphore(3)`，最多同时请求 3 条来源。
- 当前选中的来源固定优先，其他未处于冷却期的来源按内存健康评分排序。
- 单来源搜索超时为 3 秒；超时或异常不阻断其他来源。
- 结果按“规范化片名 + 年份”去重，并保持主来源优先。
- UI 显示“已完成 N/M 条线路 · 找到 X 个结果”。

### 2. 详情页渐进补线

- 主来源详情返回后立即渲染，不等待替代来源。
- 每条替代来源执行“搜索同名影片 → 请求匹配详情”的两步查询，但最多 3 条并行。
- 单条替代来源匹配超时为 4 秒。
- 每匹配到一条有效播放源，立刻将其追加进播放线路列表。
- 已找到主来源和若干可播放线路时，用户无需等待低优先级线路完成。

### 3. 内存缓存与来源健康

| 数据 | 缓存时间 | 容量 | 目的 |
|---|---:|---:|---|
| 分类/搜索/列表请求 | 5 分钟 | 80 条 | 返回页面、重复搜索快速命中 |
| 主来源影片详情 | 30 分钟 | 60 条 | 返回详情或重复点击时快速展示 |
| 来源失败冷却 | 2 分钟 | 按来源 | 避免持续请求超时或限流来源 |

- 成功请求记录近似平均延迟；失败请求进入 2 分钟冷却。
- 下次聚合搜索会跳过冷却来源，并让近期更快、更稳定的来源优先。
- 缓存和健康评分仅驻留内存，不会储存播放 URL 或用户隐私数据。

### 4. 取消与失败隔离

- 用户发起新搜索、离开详情页或取消任务时，必须重新抛出 `CancellationException`。
- 不把协程取消误判成接口失败或继续尝试备用网址。
- 单条来源失败只产生空结果/跳过，不让整个搜索或详情页失败。

## 非目标

- 不把首页分类改为多来源混合；不同 MacCMS 的分类 ID 和内容标准不一致。
- 不引入自建服务端、数据库或远程缓存；当前版本优先保持客户端实现轻量。
- 不自动访问或预加载视频媒体文件；只聚合卡片元数据和播放线路。

## 验收标准

1. 搜索页能在任一来源完成后展示已返回的卡片，并持续更新线路完成进度。
2. 同一来源同一搜索在 5 分钟内命中内存缓存，不重复网络请求。
3. 多来源搜索的同时在途请求数不超过 3。
4. 同名同年份影片只保留一张卡片，主来源优先。
5. 详情页先显示主来源；其他来源完成时，播放线路列表可见地逐步增加。
6. 慢源或失败源不会阻塞页面，且会进入短期冷却。
7. 原有分类首页、单来源备用网址、播放管家和自定义接口能力保持可用。

## 后续可选项

- 设置页提供“多来源搜索”开关及 2 / 3 / 4 条并发档位。
- 将来源健康记录持久化，并在设置页展示线路质量。
- 若未来要做跨来源首页聚合，再考虑部署后端代理、Redis 缓存和 CDN。
